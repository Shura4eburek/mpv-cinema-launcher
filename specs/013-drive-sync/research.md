# Research: Синхронизация через Google Drive

## Доступ к Drive

- **Decision**: Drive API v3 через `requests`, заголовок `Authorization: Bearer <Backend.access_token()>`, таймаут 15 с.
  - найти: `GET /drive/v3/files?spaces=appDataFolder&q=name='watchlist.json' and trashed=false&fields=files(id,modifiedTime)&orderBy=createdTime`
  - скачать: `GET /drive/v3/files/{id}?alt=media`
  - создать: `POST /upload/drive/v3/files?uploadType=multipart&fields=id,modifiedTime` с метаданными `{"name": "watchlist.json", "parents": ["appDataFolder"]}`
  - обновить: `PATCH /upload/drive/v3/files/{id}?uploadType=media&fields=id,modifiedTime`
  - метаданные: `GET /drive/v3/files/{id}?fields=modifiedTime`
- **Rationale**: `requests` уже используется; `google-api-python-client` — тяжёлая зависимость ради пяти запросов.
- **Alternatives**: `google-api-python-client` (лишние ~10 МБ в сборке).

## Ошибки

- **Decision**: `ApiError` из `access_token()`: `signed_out` → синхронизация выключена; `expired` → состояние `auth_required`; `offline` → `offline`. HTTP 401 от Drive → один раз сбросить access token и повторить, второй 401 → `auth_required`. `ConnectionError`/`Timeout`, 429, 5xx → `offline` (повтор через 60 с). 403 (квота, `appNotAuthorizedToFile`), битый JSON, `version` > 1 → `error` с текстом, ничего не пишется.
- **Rationale**: временные сбои повторяются сами, постоянные требуют внимания пользователя.

## Слияние

- **Decision**: по ключу записи; побеждает запись с большим `updated_at` (строки ISO с микросекундами сравнимы лексикографически); при равенстве — большая по `json.dumps(sort_keys=True)` (детерминированно на всех устройствах). Запись берётся целиком, поэтому неизвестные поля новой версии сохраняются. Tombstone — обычная запись с `deleted_at`, участвует в LWW. `lookups` не синхронизируются (кэш поиска id).
- **Rationale**: LWW по записи коммутативен и идемпотентен: порядок синхронизаций устройств не важен, повтор безопасен.
- **Ключи**: тайтл может лежать под запасным ключом `t:…` на одном устройстве и под `tt…` на другом. `apply_id` уже делает tombstone на запасном ключе, после слияния возможен дубль, если запасной изменён позже; его убирает следующий `watchlist_resolve` (уже существующая логика объединения). Допустимо.
- **Очистка**: tombstones с `deleted_at` старше 90 дней удаляются из результата слияния (и локально, и в облаке). Устройство, не синхронизированное > 90 дней, может вернуть такую запись — принятый риск (spec, Assumptions).

## Гонка двух устройств

- **Decision**: цикл: найти файл → скачать (запомнить `modifiedTime`) → слить с локальным → сохранить локально → перед записью снова прочитать `modifiedTime`; изменился — повторить цикл (до 3 раз), иначе записать. Ошибка после 3 попыток → `pending` остаётся, повтор позже.
- **Rationale**: Drive v3 не поддерживает условную запись по ETag; окно гонки сокращается до одного запроса, а остаток гонки закрывает коммутативность: проигравшее устройство хранит свои записи локально и отправит их снова при следующей синхронизации. Чтобы это случилось, после записи `pending` сбрасывается, только если локальный список не менялся во время цикла.
- **Дубли файлов**: если найдено несколько `watchlist.json` (одновременное создание), сливаются все, запись — в самый старый, остальные удаляются (`DELETE /drive/v3/files/{id}`).

## Поток и триггеры

- **Decision**: `Syncer` — один daemon-поток с очередью запросов («нужна синхронизация»); запросы, пришедшие во время цикла, схлопываются в один следующий цикл. Триггеры:
  - `account_changed` с `state: "signed_in"` (после восстановления при старте и после входа);
  - `Watchlist.on_change` → таймер debounce 3 с (каждое изменение переносит таймер), сразу ставит `pending: true`;
  - `sync_now`;
  - таймер 60 с, пока состояние `offline` и `pending`.
- Выход (`signed_out`) — синхронизация останавливается, таймеры отменяются, `sync.json` сбрасывает `email`; локальный и облачный списки не трогаются.
- Закрытие приложения в окне debounce: `pending: true` уже в `sync.json`, отправка — при следующем запуске.
- **Rationale**: пул `io` (4 потока) не должен занимать медленный Drive; один поток исключает параллельные циклы.

## Смена аккаунта

- **Decision**: `sync.json.email` хранит аккаунт последней синхронизации. Вход другим аккаунтом — обычное слияние локального списка с облаком нового аккаунта (spec US3/AC5), `email` обновляется.

## Локальное применение облачных изменений

- **Decision**: `merge()` идёт через `_commit` (атомарная запись, под локом списка). Если локальный список изменился, backend шлёт `watchlist_reloaded`; экраны «Мой список» и страница фильма перечитывают данные.
- **Rationale**: существующее `watchlist_changed` несёт одну запись, а слияние меняет многие.
