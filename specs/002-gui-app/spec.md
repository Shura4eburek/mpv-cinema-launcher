# Feature Specification: GUI-приложение (двойной клик)

**Feature Branch**: `002-gui-app`

**Created**: 2026-10-31

**Status**: Draft

**Input**: User description: "Нативное десктоп-приложение (GUI) поверх лаунчера mpv HLS (001): запуск двойным кликом, без терминала."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Запуск двойным кликом из буфера (Priority: P1)

Пользователь скопировал ссылку `.m3u8` в браузере. Он дважды кликает по иконке
приложения (в Dock / на рабочем столе), и фильм открывается в mpv с апскейлом —
без терминала, без ввода команд.

**Why this priority**: Это и есть суть фичи и самостоятельный MVP — «скопировал →
кликнул → смотришь».

**Independent Test**: Скопировать валидную `.m3u8`, запустить приложение двойным
кликом, убедиться, что mpv открылся и играет с нужным профилем апскейла.

**Acceptance Scenarios**:

1. **Given** в буфере обмена валидная `.m3u8`-ссылка, **When** пользователь запускает приложение (без аргументов, двойным кликом), **Then** открывается mpv и воспроизводит поток с профилем под текущую машину и пресетом по умолчанию.
2. **Given** приложение запущено из Finder/ярлыка (урезанный PATH), **When** нужно найти mpv, **Then** приложение находит установленный mpv, даже если его нет в PATH.

---

### User Story 2 - Понятные ошибки без терминала (Priority: P2)

Если что-то не так (в буфере нет ссылки; mpv не установлен), пользователь должен
увидеть понятное **нативное окно с сообщением**, а не «тихо ничего не произошло»
(терминала и stderr у приложения нет).

**Why this priority**: Без этого при любой осечке приложение выглядит «молча
сломанным». Критично для юзабилити, но вторично к самому запуску (US1).

**Independent Test**: Запустить приложение с пустым буфером → появляется диалог с
инструкцией. Запустить при отсутствующем mpv → появляется диалог с подсказкой по
установке.

**Acceptance Scenarios**:

1. **Given** в буфере нет пригодной ссылки, **When** приложение запущено, **Then** показывается нативный диалог: что скопировать ссылку и запустить снова.
2. **Given** mpv нигде не найден, **When** приложение запущено с валидной ссылкой, **Then** показывается нативный диалог с подсказкой, как установить mpv.

---

### User Story 3 - Распространяемые артефакты (Priority: P3)

Приложение должно существовать как обычный дистрибутив: на macOS — `.app`
(упакованный в `.dmg`), на Windows — `.exe`. macOS-артефакты собираются на маке;
для Windows поставляется готовый build-скрипт, которым пользователь соберёт `.exe`
на своей машине.

**Why this priority**: Превращает код в «программу, которую можно установить». Важно,
но поверх уже работающего поведения (US1+US2).

**Independent Test**: На macOS выполнить сборку → получить `.app`/`.dmg`, запустить
двойным кликом. На Windows выполнить поставляемый скрипт → получить рабочий `.exe`.

**Acceptance Scenarios**:

1. **Given** исходники на macOS, **When** запущена сборка, **Then** получается самодостаточный `.app` (с Python внутри) и `.dmg`, запускаемые двойным кликом без установленного Python.
2. **Given** исходники на Windows и поставляемый build-скрипт, **When** пользователь его запускает, **Then** получается самодостаточный `.exe`.
3. **Given** собранное (frozen) приложение, **When** оно выбирает профиль апскейла, **Then** mpv-профили находятся внутри бандла (а не только при запуске из исходников).

---

### Edge Cases

- **Пустой/непригодный буфер** → нативный диалог с инструкцией (US2).
- **mpv не найден** ни в PATH, ни в типичных местах → нативный диалог с подсказкой.
- **Профили отсутствуют в бандле** → предсказуемая деградация к встроенному апскейлу (как в 001), по возможности с уведомлением.
- **Протухшая/недоступная ссылка** → её отрабатывает mpv; приложение не виsnet, но и не «молчит» на этапе запуска.
- **Ссылка в буфере с лишними пробелами/переводами строк** → нормализуется (как в 001).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Приложение MUST запускаться двойным кликом как нативное десктоп-приложение, без терминала и без аргументов командной строки.
- **FR-002**: При запуске приложение MUST брать ссылку на поток из системного буфера обмена и валидировать её (переиспользуя логику фичи 001).
- **FR-003**: Приложение MUST запускать mpv с тем же выбором профиля апскейла под железо и пресета контента, что и CLI-лаунчер 001.
- **FR-004**: Все ошибки (нет пригодной ссылки; mpv не найден) MUST показываться нативным диалогом ОС, а не выводом в stderr.
- **FR-005**: Приложение MUST находить установленный mpv даже при урезанном PATH (запуск из Finder/ярлыка): искать в PATH и в типичных местах установки (macOS: `/opt/homebrew/bin`, `/usr/local/bin`; Windows: типичные пути установки mpv).
- **FR-006**: mpv-профили апскейла MUST поставляться внутри бандла и корректно находиться в собранном (frozen) приложении.
- **FR-007**: Приложение MUST распространяться как самодостаточный бандл с Python внутри (не требует установленного Python у пользователя).
- **FR-008**: Сборка MUST давать `.app` и `.dmg` на macOS; для Windows MUST поставляться готовый build-скрипт/спецификация сборки `.exe`.
- **FR-009**: Сам mpv в бандл НЕ входит (требуется установленный отдельно) — это зафиксированное ограничение.
- **FR-010**: Логика фичи 001 (валидация ссылки, буфер, выбор профиля/пресета, сборка команды) MUST переиспользоваться, а не дублироваться.

### Key Entities *(include if feature involves data)*

- **Расположение mpv (mpv location)**: путь к исполняемому mpv, разрешаемый из PATH или из списка типичных мест установки по ОС.
- **Ресурсы бандла (bundled resources)**: mpv-профили `*.conf`, поставляемые внутри приложения; путь к ним отличается в режиме исходников и в frozen-режиме.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: От двойного клика (при ссылке в буфере) до начала воспроизведения проходит не более нескольких секунд, без каких-либо действий пользователя кроме клика.
- **SC-002**: На машине с установленным mpv приложение находит его и запускает воспроизведение в 100% случаев, независимо от того, есть ли mpv в PATH.
- **SC-003**: Любая ошибка запуска (нет ссылки / нет mpv) в 100% случаев оканчивается видимым нативным диалогом, а не «молчаливым» бездействием.
- **SC-004**: Собранный `.app`/`.exe` запускается на машине **без установленного Python**.
- **SC-005**: Собранное приложение находит свои mpv-профили (апскейл применяется так же, как при запуске из исходников).

## Assumptions

- **GUI использует умолчания**: авто-профиль под железо и пресет `film`. Явный выбор
  «аниме» в GUI-режиме в MVP не входит (возможен позже — отдельный пункт/иконка или
  мини-диалог). CLI-лаунчер 001 остаётся для тонкой настройки.
- **Диалоги — средствами ОС без тяжёлых GUI-фреймворков**: нативный способ показа
  сообщения на каждой платформе (детали — на этапе плана).
- **Подпись/нотаризация вне scope**: при первом запуске возможны штатные
  предупреждения ОС о «неподписанном» приложении — пользователь разрешает вручную.
- **Windows .exe собирает пользователь**: кросс-сборка невозможна; на macOS собираются
  только macOS-артефакты.
- **mpv и шейдеры** на целевой машине предполагаются установленными (как в 001);
  бандл несёт только профили `.conf`, но не шейдеры и не mpv.

## Dependencies

- Работающая логика фичи 001 (`mpv_launcher`).
- Установленный mpv на целевой машине.
- Инструмент упаковки, умеющий собирать самодостаточный бандл с Python (детали — в плане).
- Для `.exe` — Windows-машина с этим инструментом (сборку запускает пользователь).
